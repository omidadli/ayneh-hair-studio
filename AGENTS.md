# Ayneh project workflow

- This project is the independently rebuilt Ayneh hair consultation application.
- Keep the GitHub repository synchronized with every user-requested code change. Commit and push the validated source to GitHub before reporting completion. If blocked, clearly report that GitHub is not synchronized.
- Preserve the Sites project identity in .openai/hosting.json and its configured audience. The current user brief requests public salon pages; keep all customer data and manager operations protected server-side. Sites remains the deployment target; GitHub stores source and runs validation, not the production Worker.
- Never commit API keys, credentials, customer photos, generated customer output or local environment files.
- Run bash scripts/build.sh and node scripts/validate-artifact.mjs before publishing.
- Do not claim live KIE generation has been tested without a successful real request.
- Salons run day to day from the Telegram/Bale bot. A salon that bought a plan also gets the key-login panel at /panel (owner's decision): its page, plan, image credits and top-ups. Unpaid salons have no panel. The bot (worker/telegram.js, one code path for both; Bale gets plain text). The owner console is /admin. Booking exists only as the owner asked for it: a salon on PRO or SIGNATURE (or the 3- or 6-month «پنل آرایشگاه») sets a day and time for a request in /panel (worker/panelapi.js, table bookings); following customers get the confirmation, a day-before reminder and one after-visit follow-up on Telegram/Bale only. Do not add customer self-booking, SMS reminders or other booking features without being asked. SMS exists only for two things the owner asked for: the one-time code that verifies a customer's mobile before generation (worker/sms.js) and the salon-link text a salon triggers from the Telegram bot. Keep MELIPAYAMAK_TOKEN secret; do not add other SMS uses without being asked.
- Catalog photos in public/catalog are generated by .github/workflows/catalog.yml; never commit placeholder images there.
- Usage stats (worker/stats.js) use only an anonymous random browser id and event names; never log names, mobiles, photos or IPs into events_log.
- Staff referrals (worker/referral.js): the first link wins and is permanent; only the salon manager moves a customer. A member's customers' requests go only to that member, never to the manager or other members. The server alone decides the owner of a request. Customer photos and submissions are kept permanently by the owner's decision; do not reintroduce automatic deletion without being asked.
- Owner alerts (worker/alerts.js): every bot action that can fail must reply to the sender in plain Persian and call notifyOwner; activity and alerts never contain customer mobiles or photos.
- Service lines (worker/lines.js): hair = hairstyle only (keeps her colour), color = hair colour only (keeps her haircut; may use her own hairstyle result as base_id), nails, lashes. The owner removed the consent checkboxes: keep the short notes under «بساز» and the send button instead of adding checkboxes back.
- Beauty consultant (worker/consult.js, client in worker/customer.js): the card and its paid vision routes exist only on the direct studio salon (`isDirect`) and only on the hair and colour lines — nails and lashes never run (nor charge) the vision. Caps are rolling 24-hour windows over hashed keys: a guest gets 1 success and 3 attempts per day keyed by browser id + hashed IP, plus a guest-only network counter (`NET_DAILY`=10 per client IP); a signed-in customer gets 30 successes and 60 attempts per phone and carries no network counter. The vision cache is keyed by the SHA-256 of the photo bytes (a hit spends nothing); the slots are reserved atomically before the call; on failure the success slot is always refunded, the attempt counter never (it counts attempts, so junk replies cannot loop), and the network counter only when the request never reached a billed answer (fetch error or HTTP non-2xx); the provider call is bounded by `AbortSignal.timeout(25000)`. Without a key the sheet falls back to the questionnaire — never invent a result. A build image attaches to a saved consultation only when the client's `fromConsult` marker and the photo match. Suggestions are deterministic rules over the service's own catalog: each card gets a distinct matched reason, or a tag-specific fallback line. Tests mock the vision endpoint — do not claim live KIE vision has been tested for this feature (the same rule as generation).
- Image quota (worker/server.js QUOTA_PER_LINE): each person (session, browser id, verified mobile) gets 3 images per service on a salon page (12 in all; the 360 view counts as hairstyle; failed images do not count). Trial and demo pages keep their own budgets. Do not raise it without the owner asking.
- Team mobiles without image limits live only in the database (app_settings key unlimited_phones, a JSON list of +98 numbers); never put phone numbers in the code or the public repo.
- Public pages (owner's decision): "/" introduces Ayneh only (benefits, sample work per service, FAQ, one CTA box per service, each addressed to that specialist). Each service has its own page built from one template: /hair (hairstyle), /color (hair colour), /nails, /lashes; plus /salon-panel (the salon panel) and /sample (the 3-step sample builder; /try is the regular customer page). The home page demo («خودتان امتحان کنید.») has four service chips. All pages are built from one source by design/landing/build.py; never hand-edit worker/landing.js. REAL_SAMPLES in build.py holds the owner's illustrative pairs, labelled «نمونهٔ نمایشی · تقریبی»; never label them «ساخته‌شده با آینه» until they are real Ayneh results.
- Plan names shown to people are Persian (owner's decision): ESSENTIAL «پایه», PRO «حرفه‌ای», SIGNATURE «کامل». ## Product QA checklist (run before every push that touches a page)
Look at every screen as a first-time customer, signed out AND signed in, on phone (390px) and desktop (1366px). For each element ask:
- Who is it for? Personal things (album, saved/liked looks, coins history) appear only for a signed-in customer; signed out they are hidden or ask her to sign in first.
- Where does this action's data go, and will she find it again? (like/save → her account → profile). No action may silently store data she can't see.
- Is it grouped by the context she is in? (trends, samples and hints follow the selected service; nothing from another service mixed in).
- Exactly one primary action per moment; no two buttons doing the same thing on one screen.
- Is every image fully and correctly framed at first sight (sliders start centred, nothing cropped to a third, no letterboxing)?
- Does state stay in its own tab/service, survive switching, and clear on sign-out?
- Empty, loading, error and "no photo yet" states look intentional; Persian copy reads naturally and matches the state.
Write the findings list first, fix all, re-shoot, and have a fresh reviewer agent check the screenshots before calling it done.

- Free signup (owner's decision, Nov 2026; worker/trial.js, /pricing «ثبت‌نام رایگان»): a professional signs up with name + mobile (SMS code when SMS is on; one per mobile; a mobile with a paid panel cannot; 8 per network per day) and gets a page /s/t-… with TRIAL_IMAGES = 3 free images (no time limit in practice: 90 days) and no OTP for its own customers (the 3 images cap it). The HttpOnly cookie «ayneh_trial» (random token, only its hash in trials.buy_token_hash, drizzle/0033) lets /pricing buy for the same mobile and page without a form (/api/trial/me shows only a masked mobile; /api/buy takes name and mobile from the signup, never from the request). The paid order turns that page into the paid salon (same id and address, settings.trial removed, trials.converted_at). The salon's own buyer (verified mobile = the paying mobile) has no per-person quota on her own page; her images come from the salon's credit.
